# What the Lite line costs

> Measured the same way for the three builds a reader could have installed: **0.1.3** (the public
> stable), **0.1.4 full/scene** (the line that kept replaying history) and **0.1.4 lite** (this one).
> The question is not which is nicer but what each one *does* per model call.

## Method

`scripts/benchmark-overhead.mjs` drives every build through the harness's own shape:

```
llm/stream dispatch → start frame → 300 token-level deltas → usage chunk → end frame
                    → settlement (assistant/message with usage and a 20-record compact stream)
                    → turn/end
```

240 settled requests × 300 deltas = 72,000 deltas per run. Each build is loaded from its own
`lib/index.js` in **its own process** (memory cannot be measured across builds), against a fake
Cordis context that records the taps, answers the plugin's route, and subscribes one reader so the
publish path is exercised rather than skipped. Every request's compact stream is its own bytes —
a store that deduplicates identical payloads would otherwise hide exactly the cost being measured.

Three things make the numbers readable rather than decorative:

- **a baseline row** — the identical workload with *nothing* installed — so the harness's own cost
  (0.143 µs/delta, 0.049 ms/request) can be subtracted and the plugin's **marginal** cost reported;
- **medians of three runs**, because the machine measuring this is also running the harness, the
  agent and the plugin itself;
- the same workload, the same machine, the same minute for all four rows.

Reproduce with `node scripts/benchmark-overhead.mjs` (it looks for the other two lines under
`~/.dsh-017/bench/{v013,full}`; point it with `--build <package dir>` for anything else).

## The numbers

240 settled requests · 72,000 token deltas · medians of 3 runs

| build | client | host | µs/delta | **marginal µs/delta** | ms/request | feed bytes | heap |
|---|---|---|---|---|---|---|---|
| *(no plugin — baseline)* | – | – | 0.143 | 0.000 | 0.049 | – | 4.5 MB |
| **0.1.4 lite** | **21.2 kB** | **30.2 kB** | 0.262 | **0.119** | **0.093** | **47,374** | 5.0 MB |
| 0.1.4 full/scene | 129.4 kB | 76.6 kB | 0.468 | 0.325 | 0.256 | 222,441 | 5.7 MB |
| 0.1.3 stable | 122.3 kB | 76.2 kB | 0.469 | 0.326 | 0.262 | 222,441 | 5.7 MB |

Marginal cost is the measured figure minus the baseline, so it is what the plugin itself spends.

| ratio | Lite vs 0.1.3 / full |
|---|---|
| client bundle | **6.1× smaller** (21.2 kB vs 129.4 kB) |
| host half | **2.5× smaller** (30.2 kB vs 76.6 kB) |
| per token delta | **2.7× cheaper** (0.119 µs vs 0.325 µs) |
| per settled request | **4.7× cheaper** (0.093 ms vs 0.256 ms measured; 0.044 vs 0.207 marginal) |
| bytes per feed update | **4.7× smaller** (47 kB vs 222 kB) |
| retained heap, 240 requests | 0.7 MB less (5.0 vs 5.7) |

## What this does and does not say

**The honest reading:** the plugin's own cost is **sub-millisecond per request in every line**. A
long answer with 1,500 deltas costs about 0.18 ms of plugin work in Lite and 0.49 ms in the full
line — nobody will feel that difference on a desktop. What a reader *does* feel, and what the table
actually shows, is **size**: a sixth of the client bundle, a quarter of the bytes pushed to the
browser on every settlement, and a quarter of the work per token in a path that runs inside the
model call.

**Where the per-delta difference comes from** is one decision: the full line folds every delta into
counters (text characters, reasoning characters, tool-call arguments) because its back face and its
inspector show them; Lite does not look at a delta at all, because a brick is a colour and a number.
The per-request difference is the same decision at settlement scale — the full line stores the
request envelope, the tool declarations, the context snapshot and the stream in a blob store and
hands the browser refs to them; Lite hands over eleven fields.

**What is not measured here:** the browser's own paint cost (the fixture suite checks correctness,
not frames), long-session behaviour beyond the 1,024-brick ring, and the cost of the **log backfill**
(one read per session, ~10–30 ms for a 300 kB artifact, ~200 ms for the 4.7 MB one on this machine —
paid once, when a reader opens that session, and never at startup).

**A caveat worth keeping:** these are medians of three on a busy desktop, not a benchmark lab. Treat
the ratios as the finding and the absolute microseconds as an indication.
